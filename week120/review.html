1お題の実行とJOIN結果の確認

背景Frosty Friday Week 120 のお題は、TPC-DS の5テーブルを GSD で合成して最後の JOIN が流れれば達成。
目的お題が通ったあとで合成後のテーブルどうしが繋がっているかを確かめる。

お題どおりに合成するとページとサイトの参照率が1.0から約0.6に下がる

お題の原文の手順

  • ① 入力を作る：Snowflake のサンプルデータ（TPC-DS）から5つのビューを作る。各 LIMIT 5000。商品だけは ITEM から取る。本資料では実行のたびに行が変わらないようビューをテーブルにした
  • ② 合成する：5つの入力の上にGENERATE_SYNTHETIC_DATA() で合成テーブルを作る（出力先は frosty_db.week_120）
  • ③ 検証する：売上に返品・ページ・サイト・商品を LEFT JOIN する SQL が流れればお題は達成

参照率が下がる理由

  • キーが別々に合成される：売上の ws_web_page_sk とページの wp_web_page_sk は別の列として合成される。数値のキーは元の値の写しではなく、元に似た値が作られる（公式：数値の列は元データに近い値を生成）。そのため売上側のキーの値がページ側に存在しなくなる
  • 実測（右の結果）：入力では売上のページキー1,846種類がすべてページ側（4,002種類）にある。お題どおりに合成すると、売上側が2,716種類、ページ側が2,528種類になり、両方にあるのは1,711種類。売上のキーの63%しかページに見つからない（サイトは70種類のうち47種類で、67%）
実行内容前提結果
お題の5テーブルを合成（2-1）入力はお題の5テーブルで計19,080行（WEB_SALES・WEB_RETURNS・WEB_ITEMが各5,000行、WEB_PAGEが4,002行、WEB_SITEが78行）。ウェアハウスは FF_W120_WH（Snowpark最適化 Medium）35秒（エラーなし）
お題の検証SQL（2-2）合成後の5テーブルを売上テーブル（WEB_SALES）に LEFT JOINエラーなく完了。8,798行が返る
参照率（3-1）売上の各行で商品・ページ・サイトのキーが相手のテーブルにある割合入力→合成後：商品 0.0144→0.0100、ページ 1.0→0.63、サイト 1.0→0.62

2join_keyによるリレーションの整合性

背景§1でページとサイトの参照率が1.0から0.6台に下がり商品は入力の時点で0.0144だった。
目的参照率を戻す修正（入力の取り直しと join_key の指定）を試す。

入力の取り直しとjoin_keyの指定で商品・ページ・サイトの参照率が1.00になる

お題の5テーブルはそのまま合成すると売上から商品・ページ・サイトを引けなくなる。直した点は2つ。

join_key の効き方

  • 公式の説明：結合に使う列を join_key に指定すると全テーブルで元の同じ値が同じ合成値になる（値は元と別の人工の値）。指定は結合する全テーブルの対応する列に同じ引数で付ける
  • 実測：join_key を付けると売上のページキー1,812種類がすべてページ側にある（サイトは39種類すべて）。付けないときは63%（§1）
  • 公式にない点：付けなかった場合に何が起きるかは公式の記述がない。§1 の原因は実測からの読み取り
  • ① 入力の取り直し：売上を先に5,000行取り、返品と商品を売上のキーで絞る。商品は全40万件から5,000件を取っただけなので売上の商品と重ならず入力の時点で参照率が0.0144
  • ② join_keyの指定：繋ぐ列に join_key を付けて合成する。付けずに合成するとページとサイトの参照率が1.0から0.6台に下がる（原因は§1の実測。キーが別々に合成される）

商品（WEB_ITEM）0.01440.01001.00
ページ（WEB_PAGE）1.00.631.00

3式と大小関係の再現性

背景GSD は列ごとの分布と列どうしの相関を学ぶ方式で式（売上額＝売価*数量）や大小関係（売価≤定価）は学ばないと考えられる。
目的式と大小関係が合成後にどれだけ成り立つかを測り、直し方（合成後の補正、合成前に業務仕様を渡す）を比べる。

合成後の補正は分布が崩れる。合成前に業務仕様を渡すと再現性が上がる

式が崩れる理由

  • 式はデータに書かれていない：売上額＝売価×数量のような基本の業務仕様も人が知っている暗黙知でテーブルには値だけが入っている。GSD は列ごとの分布と列どうしの相関を学ぶ。式や大小関係は学ぶ対象として公式に書かれていない
  • 暗黙知を形式知にするのは難しい：「合成の前に売価÷定価を列にして渡す」方法が効いたのは、人が仕様を知っていて列に書けたため。仕様のすべてを書き出すのは現実には難しい
  • コピュラ（統計的な方式）の限界：仕様を書き出さずに済ませる方法として次の§4でLLM に SQL を書かせるとどこまで再現できるかを試す

TPC-DSの売上テーブル（WEB_SALES）で、式（売上額＝売価*数量）は合成後に5,000行中2行（0.04%）で成り立つ。大小関係（売価≤定価）を直す方法の比較：

やり方売価≤定価定価と売価の相関（元0.689）平均売価（元50.53）行数
合成のまま74.6%−0.00750.364,843
合成の後で直す（売価を定価で頭打ち）99.92%0.31237.904,843
合成の後で落とす（破った行を捨てる）100%0.33635.622,366
合成の前に売価÷定価を列にして渡す99.94%0.6850.194,843

「合成の前に渡す」は売価÷定価のように列どうしの関係を列として入力に足すこと（業務仕様を渡す形）。2026-11-10の通し実行（売上テーブルの4,843行）。

実行した SQL：5通りの比較（7-8）
WITH u AS (
  SELECT '1 元' AS m, ws_sales_price, ws_list_price, ws_ship_date_sk, ws_sold_date_sk FROM FROSTY_DB.W120_STRAT.SRC
  UNION ALL SELECT '2 そのまま', ws_sales_price, ws_list_price, ws_ship_date_sk, ws_sold_date_sk FROM FROSTY_DB.W120_STRAT.SYN
  UNION ALL SELECT '3 後で直す', ws_sales_price, ws_list_price, ws_ship_date_sk, ws_sold_date_sk FROM FROSTY_DB.W120_STRAT.SYN_FIX
  UNION ALL SELECT '4 落とす', ws_sales_price, ws_list_price, ws_ship_date_sk, ws_sold_date_sk FROM FROSTY_DB.W120_STRAT.SYN_DROP
  UNION ALL SELECT '5 前に渡す', ws_sales_price, ws_list_price, ws_ship_date_sk, ws_sold_date_sk FROM FROSTY_DB.W120_STRAT.SYN_REBUILT)
SELECT m AS "方法", COUNT(*) AS "行数（元は4,843）",
       ROUND(AVG(IFF(ws_sales_price <= ws_list_price, 1, 0)), 4) AS "売価≤定価（元は1）",
       ROUND(AVG(IFF(ws_ship_date_sk >= ws_sold_date_sk, 1, 0)), 4) AS "出荷日≥販売日（元は1）",
       ROUND(AVG(ws_sales_price), 2) AS "平均売価（元は50.5）",
       ROUND(CORR(ws_list_price, ws_sales_price), 3) AS "定価と売価の相関（元は0.69）"
FROM u GROUP BY m ORDER BY m;

4合成の仕組み（入力・処理・出力）

目的GSD と LLM の入力・処理・出力を並べ、LLM の課題と比べる5つの条件が確かめることを示す。

入力はGSDが元の全行でLLMが集計値（約4KB）と業務ルールの文章

GSD

入力
元のテーブル（最大5テーブル・各20行〜1,400万行）と列の指定（join_key・categorical・replace）
→
処理
元の行から列ごとの分布と列どうしの相関を学んで生成
→
出力
合成テーブル。文字列は既定で伏せ字。join_keyの列はテーブルをまたいで同じ値が対応

LLM

入力
集計した統計（JSON約4KB）。元の行は渡さない。指示（テーブル名・9列・行数）と業務ルール6つを足す（業務ルールはBのみ）
→
処理
LLMがテーブルを作るSQLを1文書いて検査を通ったものだけ実行
→
出力
指定行数（1,067,371行）の合成テーブル。書かれなかった関係はSQLの書き方しだい

GSD の列の指定：join_key はテーブル間で同じ値を対応させる列。categorical は文字列の値を保持する。replace は文字列の書式を置換する。

LLM の課題

課題内容今回の対応
全行を渡せない全行（CSV 94MB）は約2,360万トークン（1トークン4バイトの見積）。AI_COMPLETE の窓はclaude-opus-5-5 で100万トークン。claude-sonnet-5-5 は公式の制限表に載っていない人が選んだ集計値を渡す（条件A・B）。行の一部を渡す（条件C）
書かなかった関係は再現されない集計値にも文章にも書かなかった関係（顧客と国など）はSQLに入らない。暗黙知を人が書き出す必要がある業務ルールの文章を足す（条件B）
集計値の選び方が結果を左右する集計値は測定項目を決めてから選んだため LLM に有利。GSD は全行で LLM は集計値だけなので同じ条件の比較ではない方法の優劣は決めない。行だけを渡す条件Cで有利さを確かめる

解決：行を減らす手段を2通り用意した。人が選んだ集計値（約4KB・条件A・B）とランダムに選んだ請求書40件（768行・条件C）。集計値から合成する考え方は周辺分布から合成する既存手法（MWEM・PrivBayes・MST・AIM）と同じ。

測定 SQL：元データと合成データを測る（11項目と行数）
CREATE OR REPLACE VIEW FROSTY_DB.W120_UCI.V_CHECK AS SELECT * FROM FROSTY_DB.W120_UCI.SRC;

CREATE OR REPLACE VIEW FROSTY_DB.W120_UCI.V_METRICS AS
WITH t AS (
  SELECT INVOICE::VARCHAR AS INVOICE, STOCKCODE::VARCHAR AS STOCKCODE, DESCRIPTION::VARCHAR AS DESCRIPTION,
         QUANTITY::NUMBER(18,2) AS QUANTITY, INVOICEDATE::TIMESTAMP_NTZ AS INVOICEDATE, PRICE::NUMBER(18,4) AS PRICE,
         CUSTOMER_ID::NUMBER AS CUSTOMER_ID, COUNTRY::VARCHAR AS COUNTRY, AMOUNT::NUMBER(18,4) AS AMOUNT
  FROM FROSTY_DB.W120_UCI.V_CHECK)
SELECT
  (SELECT COUNT(*) FROM t) AS "行数",
  (SELECT ROUND(AVG(IFF(ABS(AMOUNT - QUANTITY * PRICE) < 0.015, 1, 0)), 4) FROM t) AS "金額＝数量×単価",
  (SELECT ROUND(AVG(IFF(c > 1, 1, 0)), 4) FROM (SELECT COUNT(DISTINCT INVOICEDATE) AS c FROM t GROUP BY INVOICE)) AS "日時が複数ある請求書",
  (SELECT ROUND(AVG(IFF(c > 1, 1, 0)), 4) FROM (SELECT COUNT(DISTINCT DESCRIPTION) AS c FROM t GROUP BY STOCKCODE)) AS "商品名が複数ある商品コード",
  (SELECT ROUND(AVG(IFF(c > 1, 1, 0)), 4) FROM (SELECT COUNT(DISTINCT COUNTRY) AS c FROM t WHERE CUSTOMER_ID IS NOT NULL GROUP BY CUSTOMER_ID)) AS "国が複数ある顧客",
  (SELECT ROUND(AVG(IFF(INVOICE LIKE 'C%', 1, 0)), 4) FROM t) AS "キャンセル行の割合",
  (SELECT ROUND(AVG(IFF((INVOICE LIKE 'C%') = (QUANTITY < 0), 1, 0)), 4) FROM t) AS "C⇔マイナス数量",
  (SELECT ROUND(CORR(g.n, s.n), 3)
     FROM (SELECT TO_CHAR(INVOICEDATE, 'YYYY-MM') AS ym, COUNT(*) AS n FROM t GROUP BY 1) g
     JOIN (SELECT TO_CHAR(INVOICEDATE, 'YYYY-MM') AS ym, COUNT(*) AS n FROM FROSTY_DB.W120_UCI.SRC GROUP BY 1) s ON g.ym = s.ym) AS "月別の件数の形（元との相関）",
  (SELECT ROUND(AVG(IFF(HOUR(INVOICEDATE) < 7 OR HOUR(INVOICEDATE) > 20, 1, 0)), 4) FROM t) AS "営業時間外の割合",
  (SELECT ROUND(AVG(IFF(DAYOFWEEK(INVOICEDATE) = 6, 1, 0)), 4) FROM t) AS "土曜の割合",
  (SELECT ROUND(COUNT(*) / COUNT(DISTINCT INVOICE), 1) FROM t) AS "請求書あたりの行数",
  (SELECT COUNT(DISTINCT STOCKCODE) FROM t) AS "商品コードの種類";

目的ここまでの結果から合成データを使う前の判断を示し自分のデータで同じ測定をするための SQL を並べる。

元データと同じSQLで測った差が基準内かを一つずつ確かめる

使う分析に必要な項目だけを元データと同じSQLで測って基準内かを確かめてから使う。

測定SQLは次の6種類。型1はテーブルどうしの参照率、型2〜5が11項目、型6は親の属性で変わる子の行数。元データと合成データに同じSQLを流す。

測定 SQL：型1 JOINで相手が見つかる割合（次元側のキー重複も別に測る）
SELECT COUNT_IF(i.item_id IS NOT NULL) / COUNT(*)
FROM sales s LEFT JOIN (SELECT DISTINCT item_id FROM item) i ON s.item_id = i.item_id;
SELECT COUNT(item_id) - COUNT(DISTINCT item_id) AS dup_keys FROM item;
測定 SQL：型2 同じAに複数のBが付く割合（例：複数の国にまたがる顧客）
SELECT COUNT_IF(n > 1) / COUNT(*)
FROM (SELECT customer_id, COUNT(DISTINCT country) AS n FROM sales WHERE customer_id IS NOT NULL GROUP BY customer_id);
測定 SQL：型3 式が成り立つ割合
SELECT COUNT_IF(ABS(amount - qty * price) < 0.015) / COUNT(*) FROM sales;
測定 SQL：型4 月別の件数の形（相関と件数の比を併せて見る）
SELECT CORR(a.n, b.n), SUM(b.n) / SUM(a.n) AS row_ratio, COUNT(*) AS months FROM
  (SELECT DATE_TRUNC('month', ts) AS m, COUNT(*) AS n FROM orig GROUP BY 1) a
  JOIN (SELECT DATE_TRUNC('month', ts) AS m, COUNT(*) AS n FROM syn GROUP BY 1) b ON a.m = b.m;
測定 SQL：型5 割合・件数の差（営業時間外・土曜日・キャンセル行・行数・種類）
SELECT COUNT_IF(DAYOFWEEKISO(ts) = 6) / COUNT(*) AS saturday_share FROM orig;  -- syn にも同じSQLを流す
測定 SQL：型6 親の属性別の子の行数（例：キャンセル請求書と通常の請求書の請求書あたり行数）
SELECT is_cancel, AVG(n) FROM (SELECT invoice, invoice LIKE 'C%' AS is_cancel, COUNT(*) AS n FROM sales GROUP BY invoice) GROUP BY is_cancel;
